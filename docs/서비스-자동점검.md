# 서비스 자동 점검

실행 장소는 이 PC이고, 점검 대상은 운영 사이트입니다.
기본 주소: https://read-me-two-black.vercel.app

## 일정과 결과

- 매일 오전 9시: `node scripts/check-service-health.mjs`로 공개 화면, 비로그인 접근 제한, 실제 Supabase 일정 조회를 확인합니다. 한국 시간 오늘 이후 일정을 페이지별로 끝까지 조회하고, 예약 가능 일정이 있으면 예약 화면의 선택된 시간과 제출 버튼이 유효한지도 대조합니다.
- 매일 오전 9시 10분: 마지막 로그인 성공 기록이 7일(168시간) 이내이면 실제 로그인은 생략합니다. 그 외에는 테스트 계정으로 로그인 → `/my` 진입 → 로그아웃 → `/my` 재접근 시 로그인 화면 이동까지 확인합니다. 실패·대기는 다음 날 다시 시도합니다.
- 로그인 실행 또는 생략 판단 후 `node scripts/send-service-monitor-email.mjs`로 당일 결과를 한 통 보냅니다. 생략해도 메일 단계는 실행합니다. 연결 점검이 실행되지 않았다면 과거 결과를 오늘 성공으로 표시하지 않습니다.
- 신규 가입·인증 메일·실제 예약 저장을 포함한 전체 신청 점검은 사용자 요청으로 중지했습니다. 아래 전체 신청 절차는 향후 재개할 때만 적용합니다.
- 시간대는 Asia/Seoul입니다. 이 PC와 Codex 앱이 실행 중이어야 합니다.
- 정상·실패·미확인·로그인 생략 여부를 매일 메일로 받습니다. Thunderbird는 기존 독서모임 수신함을 확인하는 데 사용합니다. 채팅에는 실패·복구·새로운 준비사항만 알리며 같은 미해결 사유를 반복하지 않습니다.
- PC가 꺼져 놓친 날은 몰아서 실행하거나 메일을 보내지 않습니다. 다음 예약 시각에 재개합니다.

## 결과 메일 설정

`.env.monitor-mail.local`은 Git에서 제외되는 이 PC 전용 파일입니다.

- `MONITOR_RESEND_API_KEY`: 기존 또는 별도 Resend Sending access 키. Thunderbird/Gmail 비밀번호가 아닙니다.
- `MONITOR_MAIL_TO`: Thunderbird에서 받는 독서모임 메일 주소 한 개
- `MONITOR_MAIL_FROM`: 기존 Resend 발신 주소. 기본값은 `READ ME <onboarding@resend.dev>`입니다. 테스트 발신 주소를 쓰면 Resend 계정에서 허용된 수신 주소여야 합니다.

`node scripts/send-service-monitor-email.mjs --dry-run`으로 수신자·키 없이 본문을 미리 볼 수 있습니다. 실제 실행은 `--dry-run`을 뺍니다. 키나 수신자가 없으면 대기로 남기며 메일 성공으로 표시하지 않습니다.

한국 날짜별 발송 기록과 Resend 멱등성 키로 같은 날 중복 발송을 막습니다. 통신 실패 후 재시도할 때에는 첫 시도의 본문을 그대로 사용합니다. 메일 기록의 `accepted`는 발송 서비스 접수이며 실제 받은편지함 도착을 뜻하지 않습니다. 최초 설정 후 Thunderbird에서 수신을 확인합니다.

메일 기록은 `.codex-tmp/service-monitor/email-latest.json` 및 날짜별 `email-YYYY-MM-DD.json`에 보관합니다. 비밀번호·키·수신 주소·회원 정보는 기록하지 않습니다. `email.lock`이 남으면 실행 중인 프로세스가 없는지 확인한 뒤 잠금을 정리하고 재시도합니다.

## 준비 정보

`.env.monitor.local`에 테스트 계정 이메일과 비밀번호, 모집 시작 예정 시각을 입력합니다. 이 파일은 기존 `.env*.local` 규칙으로 Git에서 제외됩니다. 비밀번호나 세션을 출력하거나 보고서에 저장하지 않습니다.

전체 신청 점검에는 다음 준비가 추가로 필요합니다.

1. 신규 가입에 쓸 테스트 전용 이메일과 인증 메일을 읽을 수 있는 연결
2. 테스트 이름·이메일에 대한 가입 승인 명단 및 필요한 사전 신청 상태
3. 테스트 전용 인터뷰 시간과 해당 예약을 확인할 운영자 계정
4. 이번 실행이 만든 항목의 ID를 기록하고 그 항목만 정리하는 절차

준비가 없으면 **대기**로 기록합니다. 일반 회원·예약을 대신 사용하거나 메일 인증을 우회해 통과로 보고하지 않습니다. 일일 연결 점검 성공은 전체 신청 성공을 의미하지 않습니다.

### 인터뷰 예약 제출 점검 추가 준비

2026-11-03 사용자가 예약 제출 점검 추가를 승인했습니다. 신규 가입·인증 메일은 계속 제외합니다. 예약 화면 수정 배포 및 테스트 전용 일정·관리자 화면 확인·정리 절차 준비 후 정기 점검을 활성화합니다. 준비 전에는 실제 예약 저장을 성공으로 보고하지 않습니다.

현재 신청자 문자·알림톡 웹훅은 운영 환경에 설정되지 않았고 운영자 예약 이메일은 설정돼 있습니다. 본인 번호 대신 테스트 값 `010-0000-0000`을 고정 사용합니다. 매 실행 직전 신청자 발송 연결이 없는지 다시 확인하며, 연결되었거나 확인할 수 없으면 제출하지 않고 대기로 기록합니다. 운영자 이메일에는 테스트 예약 알림이 생길 수 있습니다. 임의의 다른 번호나 일반 회원의 번호는 사용하지 않습니다.

2026-11-03 장애: DB의 달력 일정 1,856개 중 앞 1,000개만 받아 미래 예약 가능 시간 400개가 누락됐습니다. 통신 성공만으로 정상 처리하던 점검을 보강했습니다. 화면의 시간 선택 검증은 실제 예약 저장 검증을 대신하지 않습니다.

## 자동 실행 절차

매 실행 전 이 문서를 읽습니다. 일일 연결 점검 결과는 `.codex-tmp/service-monitor/health-latest.json` 및 시각별 JSON에 저장합니다. 로그인 점검은 별도 브라우저 세션으로 진행하고, 성공·실패 여부와 실패 구간만 저장합니다.

전체 점검은 운영 배포의 식별자를 확인할 수 있으면 마지막 성공한 식별자와 비교합니다. 로컬 Git 커밋을 운영 배포로 간주하지 않습니다. 배포 정보가 없으면 변경 여부를 알 수 없다고 기록합니다. 모집 시각은 `MONITOR_RECRUITMENT_START`를 사용하며 기수 시작일로 대체하지 않습니다.

전체 점검은 신규 가입 및 이메일 인증 → 필요한 초기 정보 입력 → 인터뷰 신청 → 운영자 화면 반영 확인 → 이번 실행의 테스트 예약 및 신규 계정 정리 순으로 진행합니다. 현재 회원가입에는 승인 명단이 필요하므로 사전 준비도 확인합니다. 운영 사이트의 정상적인 경로를 사용하고, 실제 사용자 알림이나 공개 예약 시간을 테스트에 사용하지 않습니다. 전용 알림 수신자와 정리 방법이 확인되지 않으면 저장 전에 대기합니다.

검증하지 못한 단계는 미확인으로 남기고, 전체 성공 시에만 배포 식별자·모집 시각별 완료 상태를 기록합니다. 정리 실패는 반드시 알립니다. 코드를 자동 수정하거나 커밋·푸시·배포하지 않습니다.
